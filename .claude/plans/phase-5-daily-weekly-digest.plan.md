### 0.1 三个裁决为什么这样定

**D1 确定性渲染。** Phase 4 plan §6 把「把雷达讲成人话」划给了本阶段，但仓库**零 secrets**（Phase 3 plan §1.4），没有服务端 LLM。上游 follow-builders 的模型是 `prepare-digest.js` 产出「feeds + prompts」的 JSON，**文案由消费端的 LLM 写**（实测：`scripts/prepare-digest.js:11-13`）。若沿用该模型，本仓库交付的是**准备工作**，不是 digest —— Exit Criteria 的「能生成含来源链接的日报」无法自证，且 LLM 那一层不可 gate、会随 prompt 漂移而腐化。

选确定性渲染还有第二个理由：**「判断」在 Phase 3/4 已经算完了。** 主题权重、环归属、动量都是规则化的结论，`ringReason` 已经是一句机器写的判断句（`momentum +0.405 >= 0; breadth 13 >= 3; … -> adopt`）。Phase 5 的活是把它**译成人话并组织起来**，不是重新判断。这与 Phase 4 §0.1 的划分一致：**规则化的判断在结构层，叙述在文案层** —— 只不过本阶段的「叙述」是模板，不是 LLM。

> **被否掉的两个选项**：（a）只产出 LLM 上下文 + prompt —— 沿袭上游，但不可验证、不可复现；（b）两层都做 —— 多出的 LLM 层不可 gate，会腐化，且今天没有消费者。

**D2 增量 + 全窗。** 日报与周报回答的是**两个不同的问题**：日报答「今天生态里新增了什么、它落在哪个成熟度」，周报答「这一周各主题成熟度长什么样、有没有换环」。若两者都只渲染整窗口雷达，日报就失去时间锚点，读起来每天一样；若两者都只看增量，周报就退化成七份日报的拼接，看不出趋势。

**D3 只提交最新一份。** digest 是**派生产物**，按 CLAUDE.md §5 的精神本不该入 Git（同 `signals.json`）。但它又是整条链路**唯一的人可读产物** —— 其他全是 JSON。折中：只保留最新一份、每次覆写，文件数恒为 2、体积有界（实测量级 ≈ 数 KB）。按日期归档会让仓库随时间无界增长，与「小且有界」冲突。

### 0.3 首版实测（本地渲染，2026-09-29）

```
日报 digest-daily.md    102 行 · 5,951 bytes · 今日新增 48 条（本地口径，见下）
周报 digest-weekly.md   131 行 · 5,582 bytes · 9 扇区 · 环移动「本周无环变动」
```

三件必须如实说明的事：

1. **日报的「今日新增」是本地口径，不是 CI 口径。** 本地工作区里 `signals.json` 与 `signals-window.json` 同属**更早的一次本地运行**（148 signal），而 `topics.json` / `radar.json` 是**CI 产物**（172 signal）—— 两者来自不同批次。因此本地渲染出的「48 条增量为真、其余为未归类」这个比例在 CI 上会变。**这不是代码问题**：CI 里四份输入产自同一次运行。已提交的这两个文件会被下一次 CI run 覆写为一致口径的版本。
2. **周报的环移动是「无变动」** —— `radar.json` 在 git 里只有 1 个提交（§1.4），首份基线与自己相同。降级路径（§4.4）按设计生效。
3. **周报的链接里有相当一部分没有标题**（形如 `- https://…`）—— 同样是本地批次不一致造成的：cluster 的 `signalIds` 要 join `signals-window.json` 才能取到标题（§1.3），而本地 window 只覆盖 148 个 signal。CI 里 `topics.json` 正是从同一份 `signals-window.json` 建出来的，**每个 cluster 的 signalId 必然可在 window 中解析**。这一点本地无法完全验证，但由构造保证。

## 1. 背景与关键事实（均为实测）

### 1.1 三份输入，全部已在仓 / 已在 CI 工作树

| 文件 | 位置 | 本阶段用它做什么 |
|---|---|---|
| `topics.json`（74 KB，**已提交**） | 仓库根 | 主题 → 环的映射底料：9 个 topic + 170 个 cluster（每个带 `primaryUrl` / `sourceDiversity` / `publishedAtLatest` / `weight`）；`unclassified.signalIds`（82 条） |
| `radar.json`（7.7 KB，**已提交**） | 仓库根 | 环归属与判断依据：每扇区的 `ring` / `breadth` / `momentum` / `recentClusters` / `priorClusters` / `weight` / `ringReason` |
| `signals-window.json`（274 KB，**gitignored**） | CI 工作树 | **标题解析**：cluster 只有 `primaryUrl` 没有 `title`，标题要从 signal 取（signal 带 `title` / `url` / `source_id` / `published_at`） |
| `signals.json`（**gitignored**） | CI 工作树 | **日报的增量**：跨 run 去重后的产物 = 自上次运行以来的新信号 |

**本阶段只读这四份，不读 `signals-internal.json`**（internal 无下游通路，Phase 3 plan §4.3）。

### 1.2 现有 digest 链路是「消费端 LLM」模型（实测）

`scripts/prepare-digest.js` 把 feeds + `prompts/*.md` 打成一个 JSON blob，注释写明（`prepare-digest.js:11-13`）：

> The LLM's ONLY job is to read this JSON, remix the content, and output the digest text.

`prompts/` 里的五个文件（`summarize-{podcast,tweets,blogs}.md` · `digest-intro.md` · `translate.md`）**是给那个 LLM 的指令**，描述的是 follow-builders 的 builder digest（按 X / 官方博客 / 播客分节），**不是**主题 / 雷达视角。`scripts/deliver.js` 是投递层（Telegram / Resend / stdout），**属于 Phase 6 的接口**，本阶段不动。

**含义**：本阶段**不接**这条 LLM 链路。它保留在仓里，作为「若将来要 LLM 润色」的现成入口，但不进入 Phase 5 的产物路径。

### 1.3 链接与标题都可解析（实测，这是 D1 可行的前提）

- `topics.json` 的 **170 / 170** 个 cluster 都带 `primaryUrl` —— **没有一条内容是无法给出链接的**，§7 的「链接强制」不会因为上游缺字段而空转。
- `unclassified` 带 82 个 `signalIds` —— 未归类的内容**同样可以给出链接**，不必静默丢弃。
- 标题不在 `topics.json` 里，必须 join `signals-window.json`（§1.1）。

### 1.4 周报的跨 run 对比今天只有 **1** 个数据点（实测）

`git log -- radar.json` → **1 个提交**（`c39649a`，Phase 4 交付那次）。也就是说「对比上一份 `radar.json`」今天拿不到有意义的前任。

**含义**：环移动对比必须**有则报、无则降级**（§4.4），不能在头几天输出瞎编的移动，也不能因为没有前任而失败。这与 Phase 4 plan §1.4 对「跨 run 权重序列」的处置同一口径：**依赖时间累积的东西，今天不成立，就降级并如实说明。**

### 1.5 `prompts/` 的两条规则被本阶段**继承为结构约束**

上游 prompt 里有两句，与本仓库宪章是同一条：

1. `digest-intro.md:43-49`「**Mandatory links** … If you don't have a link for something, do NOT include it. **No link = not real**」—— 对应 PLAN.md 全局约束 3（来源可追溯）。
2. `digest-intro.md:51-55`「**No fabrication** … NEVER make up quotes, opinions, or content you think someone might have said」—— 对应确定性渲染的天然属性：模板只填**已经算出来的量**，不生成新事实。

本阶段把第 1 条**代码化**（gate `G2`），第 2 条由 D1 的选择天然满足。

## 2. Digest 的语义（D1 — 确定性渲染）

**digest 的「组织」= 雷达的结构，digest 的「判断」= 规则生成的结论句。**

日报 / 周报不是「今天的新闻列表」，而是**按生态注意力的成熟度组织的一份读数**：先说结论（这个主题处在哪个环、在升还是在退），再给证据（几个源、前后半段各多少事件），最后给链接（人自己去读）。

**判断句由谁写**：由 `lib/digest.js` 的模板，输入是 `radar.json` 里**已经算好的** `ring` / `momentum` / `breadth` / `recentClusters` / `priorClusters`。模板**只填数、不做新判断、不生成事实** —— 这是它与 LLM 的根本区别，也是它可 gate 的原因（gate `G4`）。

> **一句话区分**：LLM 会「读完之后给你写一段感想」；本阶段是「把已经算好的读数译成人话」。两者的可信度不同 —— 前者不可复现，后者逐字节可复现。

## 3. 日报与周报的输入（D2 — 增量 + 全窗）

| | 回答的问题 | 主输入 | 组织方式 |
|---|---|---|---|
| **日报** | 今天新增了什么？落在哪个成熟度？ | `signals.json`（增量）+ `radar.json`（全貌） | 新信号**按其主题所在的环**分组，环的顺序 `adopt > trial > assess > hold`；未归类的进末尾显式标注的池区 |
| **周报** | 这周各主题成熟度如何？有没有换环？ | `topics.json`（全窗）+ `radar.json` + `prev radar.json` | 先报**环移动**（对比前任），再按环列**全部 9 个扇区**的判断句 + 代表链接 |

**日报为什么要 join `topics.json`**：`signals.json` 的信号没有 `topic` 字段。要做「按环分组」，得先用 `topics.json` 的 `clusters[].signalIds` 建 `signalId → topic` 映射，再用 `radar.json` 把 topic 映到环。

**边界情况**：
1. **增量为空**（安静的运行日，CI 里 `signals.json` 可能只有几条甚至 0 条）：日报仍要产出 —— 输出「今日无新增信号」，后接雷达全貌。**空不是失败**（gate `G9`）。
2. **周报的前任缺失**（§1.4）：省略环移动小节并写明「无对比基线」，不报错、不编造（gate `G8`）。

## 4. 渲染规则

### 4.1 判断句模板（按环）

模板输入：`ring` · `momentum` · `breadth` · `recentClusters` / `priorClusters`。四条环各一句，**只填已算好的量**：

| 环 | 模板（最终文本，与 `lib/digest.js` 一致） |
|---|---|
| `adopt` · 动量 > 0 | `覆盖广（{breadth} 个独立源）、动量温和为正（{momentum}）—— 生态已收敛且仍在缓升。` |
| `adopt` · 动量 = 0 | `覆盖广（{breadth} 个独立源）、动量持平 —— 生态已收敛，处于稳定期。` |
| `trial` | `覆盖达标（{breadth} 个独立源）且动量急升（{momentum}）—— 共识形成前的活跃试验期。` |
| `assess` · 动量 > 0 | `有升势（{momentum}）但独立源偏少（仅 {breadth} 个）—— 只够放进观察位。` |
| `assess` · 动量 = 0 | `动量持平但独立源偏少（仅 {breadth} 个）—— 只够放进观察位。` |
| `assess` · 动量不可测 | `窗口内有事件但均无发布时间 —— 方向不可测，只够放进观察位。` |
| `hold` · 动量 < 0 | `动量转负（{momentum}，{breadth} 个源）—— 注意力在退。` |
| `hold` · 无活动 | `窗口内无任何活动。` |

**两条体裁规则**（都是 gate 断言的对象，不是措辞偏好）：

1. **凡是断言了方向的句子，必须把动量印出来**（`adopt`/`trial`/`assess` 的上升分支、`hold` 的下降分支）。说「有升势」却不给 `+1.00`，读者无法复核 —— 与 Phase 4 §4.3「环的判定必须可解释」同一条原则。
2. **`momentum = 0` 不得写成「有升势」。** 这条是 gate 抓出来的真实缺陷（`inference-and-cost` 当时读数恰好为 0）—— 见 §7.3 的规则。

**`assess` 有三个分支不是疏忽**：`decideRing` 里 `assess` 可以由两条不同的路径到达 —— 「有升势但源太窄」与「`dated === 0`，方向根本测不出来」（Phase 4 plan §4.1 第 2 条）。两条路径的句子必须不同，因为它们是两件不同的事。**gate `G4` 曾在这里断言错**（要求「不可测」那一支也印广度），正是 §7.4 的 M1。

**为什么模板要带数**：与 Phase 4 §4.3「环的判定必须可解释」同理 —— 读者要能自己复核结论，不必读代码。数字写进句子，判断就不是空话。

### 4.2 排序与截断（必须确定性）

| 位置 | 排序 | 理由 |
|---|---|---|
| 环分组的顺序 | `adopt > trial > assess > hold` | §2 |
| 环内扇区 | **taxonomy 声明顺序**（同 Phase 4 §5.2） | 跨时间稳定 |
| 扇区内的 **cluster**（周报） | `weight` 降序，同值时 `clusterId` 字典序 | 没有稳定 tiebreak 会破坏 `G1` 的逐字节确定性 |
| 扇区内的 **signal**（日报） | `published_at` 降序，同值时 `id` 字典序 | **与上一条有意不同**：signal 身上没有 `weight`（权重是 Phase 3 算在 topic/cluster 上的），拿不到就退到「最新在前」。这是对 §4.2 的**已知偏离**，记在这里而不是静默绕过 |
| 同级比较的实现 | **不用 `localeCompare`** | 默认排序取决于运行时 locale，是确定性的一个洞。改用码位比较（`cmpStr`），与 `G1` 同一条理由 |
| 每节的条目数 | 截断到前 N（默认 5），余量写「还有 N 条」；**N 计的是实际打印出来的条目数，不是被选中的条目数** | 手机屏可读（继承 `digest-intro.md:59`）；无链接的条目会被剔除，若按选中数计就会多报 —— 见 §7.4 的 L4 |

### 4.3 链接强制（继承 §1.5 的第 1 条）

**没有链接的条目不得出现在 digest 里。** `primaryUrl` 为空的 cluster、`url` 为空的 signal 一律剔除，并让 gate `G2` 守住。

### 4.4 环移动（周报，有则报、无则降级）

对比 `radar.json` 与 `prev radar.json` 的同名扇区：

```
moved     = { T : prevRing(T) != ring(T) }        // 换环
appeared  = { T : T 不在 prev 里 }                 // 新扇区（主题表变了才会有）
```

- 有前任且有移动 → 逐条写 `T: 待观察 → 试用中（动量 +1.00，源 3）`
- 有前任、无移动 → `本周无环变动。`
- **无前任** → 整节省略，并写明 `无对比基线（首份 radar.json）`。
- **前任的主题表不同**（`taxonomyVersion` 不一致）→ **同样降级**，写明 `无对比基线（基线主题表 v0 ≠ 当前 v1，环不可比）`。`radar.js` 专门把 `taxonomyVersion` 带进产物，就是为了让两份雷达不会被跨主题表比较（Phase 4 plan §5.1）；这里若忽略它，就等于**把「主题表变了」当成「生态变了」报出去** —— 见 §7.4 的 M2。

**只提交 `digest-daily.md` / `digest-weekly.md`，每次覆写。** 加进 workflow 的 `git add` 列表。

- **为什么入 Git**：它是整条链路唯一的人可读产物；Phase 6 也能用 raw URL 直接取（`prepare-digest.js` 已经用这个模式取 `feed-blogs.json`）。
- **为什么只留最新**：归档会无界增长。它的「历史价值」低 —— 环的跨时间记录已经在 `radar.json` 的 git 历史里，digest 只是当日的一个视图。
- **CI 里的一个防御**：提交步骤用 `[ -f ]` 守卫后才 `git add` 这两个文件。`git add` 遇到不存在的路径会**致命退出**，若不守卫，一次 digest 生成失败会连带把**当天所有 feed 的提交**一起弄挂 —— 失败应该被放大成一条断言（`Assert digest`），而不是变成第二个故障。

`signals.json` / `signals-window.json` / `signals-internal.json` 仍不提交。

## 6. 与其他阶段的边界

| 阶段 | 边界 |
|---|---|
| Phase 3 | 提供 `topics.json`。**不修改** signal 的生成 / 归一 / 去重 / 分类 / 权重 |
| Phase 4 | 提供 `radar.json`。**不重算**环、不重算权重、不再施加衰减 |
| **Phase 6（飞书）** | 本阶段产出 digest **文本**；把它**投递**出去是 Phase 6。`deliver.js` 属 Phase 6 接口，本阶段不动 |
| 上游 `prepare-digest.js` / `prompts/` | 保留现状，**不进入本阶段产物路径**（§1.2） |

**最容易越界的两处**：

1. **退化成新闻摘要。** 把 digest 写成一串标题 + 链接就是越界 —— 它必须**先给判断（环 + 动量），再给证据，最后给链接**（§2）。
2. **引入 LLM。** 任何「调模型生成文案」的做法都违反约束 6（零 secrets）与 D1。

- [x] 同输入两次运行逐字节相同 —— gate `G1`
