### 0.1 四个裁决为什么这样定

**D1 交互卡片。** 三种形态里只有卡片能同时保住标题层级、加粗和链接（`card.schema 2.0` 支持 `{"tag":"markdown"}`，官方文档 §发送飞书卡片）。纯文本会把 `**加粗**` 和 `|表格|` 原样打在群里；富文本 `post` 要另写一个 Markdown→标签结构的转换器，代码量最大而收益不高于卡片。

> **一处曾经写错的未知（2026-09-29 独立审查后更正）**：本节原来写「官方文档**没有说明**卡片的 markdown 元素是否渲染表格」—— **这是错的**。富文本组件文档写得很清楚：支持渲染表格，并给出限制「**除标题行外，最多展示五行数据，超出五行将分页展示。不支持自定义。**」digest 的「当前雷达」表有 **9 行数据**，真按表格发只会显示 5 行、其余靠分页。**所以结论不变（仍降级为列表），但理由换了**：不是「不知道能不能渲染」，而是「渲染了也不如列表全」。产物仍是标准 Markdown（`digest-*.md` 不动，形态适配只发生在投递层）—— gate `G11` 守这条。

**D2 接现有 workflow 末尾。** 独立 workflow 看起来更解耦，但它只能读**已提交**的 digest，于是必须与 feed run 错开时间，否则读到上一版 —— 引入一个无谓的竞态。接在同一 run 末尾则用的是刚刚生成、就在工作树里的文件。代价：CI 多一个依赖 secret 的步骤（而仓库今天已有两个这样的步骤，形态一致）。

**D3 分片。** 当前产物 5.6–6.0 KB，离 20 KB 有 3.5 倍余量，但 `--top` 调大或某周信号变多都会涨。截断会丢内容，「超限即失败」会把一次大周报变成一条静默的红步骤 —— 两种情况都比分片差，而分片只是按 `## ` 边界切开，代码量很小。频率上限 5 次/秒，分片完全用不到。

**D4 签名校验。** 飞书提供关键词 / IP 白名单 / 签名三种。**IP 白名单在 GitHub Actions 上不可行**（runner IP 不固定），直接排除。剩下两种里，关键词只是「消息里必须含某个词」，挡不住拿到 URL 的人；签名是 HMAC-SHA256，用 node 内置 `crypto`、零依赖，能让「URL 泄漏」不等于「可任意投稿」。这与本仓库既有的谨慎口径一致（Phase 2C 决定 internal 产物不上传 artifact，理由就是 public fork 上谁都下得到）。

| # | 行为 | 为什么 |
|---|---|---|
| 1 | **正文里的 H1 被摘掉**，标题只由卡片 header 承载 | digest 第一行是 `# Agent Technology Radar — 日报 — 2026-09-29`，而 header 渲染的就是同一串。留在正文里就是紧跟 header 的一个一级标题，白占版面。**产物不动**（gate `G11`），摘除只发生在投递层那一次转换里 |
| 2 | **非 JSON 的 2xx 算失败** | 飞书一律以 JSON 应答。拿到 HTML 说明中间隔着代理或门户页，此时**没有证据**卡片送达。原来的实现把它记成成功 —— 那正是约束 4 禁止的静默失败 |

| 6 | **非空行全是标题 = 拒绝投递** | 那种文件过得了一般的「有标题」检查，标题上提之后正文是空的，会发出一条空卡片 —— 比不发更糟。见 §7.4 发现 2 |

## 1. 背景与关键事实（实测 + 官方文档）

### 1.1 现有投递代码是上游模型，不适用

`scripts/deliver.js` 支持 telegram / email(Resend) / stdout，读 `~/.follow-builders/config.json` 与 `.env`，依赖 `dotenv`。它是 follow-builders 的**消费端**模型（给人本地跑），不是 CI 投递。`SKILL.md` 里提到的飞书是走 `openclaw` 网关（`openclaw cron add --channel feishu`），本仓库没有 openclaw。

**全仓库今天没有任何飞书 / webhook 代码**（`grep -ri feishu` 只命中 PLAN.md 与 SKILL.md 的说明文字）。

### 1.2 飞书自定义机器人的硬限制（官方文档，2026-09-29 核对）

来源：<https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot>（该站提供 `.md` 纯文本版）

| 项 | 值 |
|---|---|
| **请求体大小** | **≤ 20 KB**（超出即失败） |
| 频率 | 单租户单机器人 **100 次/分钟、5 次/秒**；官方**建议避开 10:00 / 17:30 等整点与半点**，否则可能触发 11232 限流 |
| `msg_type` | `text` · `post`(富文本) · `image` · `share_chat` · `interactive`(卡片) |
| 卡片结构 | `{"msg_type":"interactive","card":{"schema":"2.0","body":{"elements":[{"tag":"markdown","content":"…"}]}}}` |
| 签名算法 | 以 `timestamp + "\n" + 密钥` 为**密钥**，用 HMAC-SHA256 对**空字符串**求签名，再 Base64；`timestamp` 为秒级、**距请求不得超过 1 小时** |
| 安全设置 | 自定义关键词 / IP 白名单 / 签名校验（三选一或组合） |

> **一处数字冲突，已按官方取值**：第三方文档（Tapdata）写「文本 150 KB / 卡片 30 KB」，那是**应用型 IM API**（`receiveType/contentType`）的限制，**不是自定义机器人 webhook 的**。自定义机器人以官方的 **20 KB** 为准。

### 1.3 产物形态与体量（实测）

```
digest-daily.md    5.6 KB
digest-weekly.md   5.6 KB（CI 口径，171 signal）
```

产物是 Markdown，含**一张表格**（`## 当前雷达`）+ 若干 `### / ####` 小节 + 列表。体量离 20 KB 有余量，但见 §4。

### 1.4 digest 已经在 CI 里生成并被提交

Phase 5 的 `Build digest` 步骤产出 `digest-daily.md` / `digest-weekly.md`，`Assert digest is current and covers every sector` 保证它不是陈旧的，`Commit and push feeds` 提交它们。**本阶段只需在同一个 run 的末尾读这两个文件**。

## 2. 投递形态（D1 — 交互卡片）

发一条 `msg_type=interactive` 的卡片：

```jsonc
{
  "timestamp": "1730000000",
  "sign": "…",
  "msg_type": "interactive",
  "card": {
    "schema": "2.0",
    "header": { "title": { "tag": "plain_text", "content": "Agent Technology Radar — 日报 2026-09-29" } },
    "body": { "elements": [ { "tag": "markdown", "content": "<digest 正文>" } ] }
  }
}
```

**发送前的两步适配**（都在投递层，产物不动）：

1. **摘标题**：首行的 `# …` 上提到卡片 header，正文里不再重复（§0.4 #1）。
2. **表格降级**：`| a | b |` / `| --- | --- |` 结构转成 `- **a**：表头=值 · …` 形式 —— 表头行不作废，而是变成数据行的标签，所以一行仍是「环=已确立」，而不是孤零零一个数字。理由见 §0.1：飞书表格只显示 5 行数据，列表能显示 9 行。
3. **裸 URL 链接化**：`https://x` → `[https://x](https://x)`。依据：富文本组件文档称其兼容 CommonMark，而 CommonMark **不会**把裸 URL 自动变成链接；文档列出的超链接语法是 `[文字](url)`。digest 里的 URL 全是裸的，不改就是一堆不可点的纯文本 —— 而「链接可点击」正是本阶段的完成定义之一。（独立审查发现 4）
4. 其余 markdown（`##` / `###` / `**` / 列表）原样保留。

## 3. 触发与时机（D2 — 现有 workflow 末尾）

在 `generate-feed.yml` 的 `Commit and push feeds` **之后**新增一步 `Deliver to Feishu`：

- 日报：每日 run 都发。
- 周报：仅当「今天是约定的那一天」才发（避免每天发两次）。**已定：周一（UTC）**，覆盖刚结束的那一周；常量 `WEEKLY_DELIVERY_WEEKDAY` 写在 `lib/feishu.js`，`--force-weekly` 可越过。

**secret 缺失时的行为**（§0.3）：`FEISHU_WEBHOOK_URL` 未设 → 打印一行明确 warning 并 **exit 0**，不红。与 `Generate feeds` 的红不同 —— 那一步红是「已知且文档化的」，本阶段不能再用这个理由。**只设了 URL 没设 secret 则是报错**（§0.4 #4），因为那是配错，不是没配。

## 4. 分片（D3 — 按节）

```
载荷 = 卡片 JSON 序列化后的字节数
若 > SPLIT_THRESHOLD（留安全余量，如 18 KB）→ 按 "\n## " 边界切成 N 条
每条独立签名、独立发送；条与条之间不需要等待（5 次/秒上限，正常只有 1–3 条）
```

- 切分**只在 `## ` 边界**，不切断小节内部；单节本身超限则退化为按行切。
- **预算（18432 B）是打包目标，不是承诺。** 单行装不进预算时它独占一条，于是会出现落在 18432–20480 B 之间的分片 —— 允许，因为仍低于飞书的硬上限。gate `G3` 用一个 19 KB 单行的 fixture 断言这一段，而不是假装它不存在。
- **单行本身 ≥ 20 KB 时大声失败**（exit 1，错误信息带字节数）—— §0.4 #3。这是本阶段唯一拒发的输入。
- 预算按**可能的最宽后缀**（` · 第 999/999 条`）度量，而不是按当前这一条的真实标题 —— 否则「先判断装得下、再才知道真实条数」循环依赖，最后一条会悄悄超预算。
- 分片的**元信息**（第 k/N 条）写在卡片标题里，读者能看出是连续的。

---

## 5. 签名（D4）

```
stringToSign = `${timestamp}\n${secret}`
sign         = base64( HmacSHA256(key = stringToSign, message = "") )
```

`timestamp` 为**秒级**、距发送不超过 1 小时。用 `node:crypto`，零新依赖。secret 从 `FEISHU_WEBHOOK_SECRET` 读（与 URL 分开两个 secret，便于只轮换一个）。

| `G7` | **失败可观测** | 非 2xx / 非零 `code` / 非零 `StatusCode` / **非 JSON 的 200** / 带 code 的 200 之外 / 连接被拒 → **exit 非 0** 且错误信息带得出原因 | M9 |
| `G8` | **成功路径（跨 socket）** | mock 收到 N 条：POST + `application/json`、`msg_type=interactive`、`schema=2.0`、签名自洽、**到达顺序即分片顺序**、拼回等于正文、exit 0、stdout 干净 | M17 |
| `G8b` | **默认不触网** | `--print` 即使配了 URL 也**零请求**；开 socket 只由 `--send` 触发 | M12 |
| `G9` | **链接可点** | 每条 URL 都在 `[url](url)` 内、**链接文字即目标**、**无裸 URL 残留**（剥掉全部链接构造后不该再有 `https://`）；含「URL 紧贴 `*` 强调符」一例（真实 footer 的形状） | M19 · M21 · M22 |
| `G10` | **无 tier / 按源加成** | 扫描 `/\btier/i` + 具体 registry 源 id | M14 |
| `G11` | **不碰产物** | 跑完 `digest-daily.md` / `digest-weekly.md` / 源 fixture **逐字节不变**，且仓库根目录无增删文件 | M15 |
| `G12` | **坏输入 fail-fast** | 缺文件 / 空文件 / 无 `#` 标题 / **通篇只有标题** / 未知 `--mode` / 缺 `--mode` / 坏 `--now` 全部报错退出；**单行 ≥ 20 KB 也报错退出** | M16 · M20 |
| `G13` | **周报只在周一发** | 周二 `--send` → exit 0 + 零请求 + 提示「周一」；周一或 `--force-weekly` 才发；日报不受星期限制 | M3 |

> **gate 不触外网。** 它在本机 `127.0.0.1` 上起一个临时 HTTP server 冒充飞书 —— 载荷、签名、分片数、失败路径全都真的过了一遍 socket，这是离线能拿到的最强证据。**但它不等于投递到真实群**（§7.2）。
>
> **异步 spawn 是必需的**：`spawnSync` 会阻塞本进程的事件循环，mock server 就永远应答不了，每条 `--send` 检查都会卡到客户端自己的 15 秒超时。

### 7.2 无法验证（必须诚实标注）

- **端到端真实投递** —— 需要真实 webhook；CI 里能验，本地只能验到载荷。

### 7.4 独立证伪审查（`CLAUDE.md` §3.2）

交付前跑了一次**无作者上下文**的独立审查，指令是**证伪**而非确认。它给的发现，**我逐条重跑复现后才采信**。四条全部为真，全部已修：

| # | 发现 | 我的复现 | 处置 |
|---|---|---|---|
| 1 | **G5 对「丢行」是瞎的**：fixture 只有 3 行、检查硬编码 `=== 3`，所以「表格只取前 5 行」这种 bug 能让 gate **14/14 全绿** | 把 `block.slice(header ? 1 : 0)` 改成 `.slice(0, 5)` → gate 14/14 绿；而真实雷达表有 **9** 行 | fixture 换成与真实表同形的 **9 行 × 5 列**，期望输出由 gate **按表数据自己算**逐字比对 —— 变异 **M18** 现在会红 |
| 2 | **只有标题的 digest 会发出一条空卡片** | `printf '# Only A Title\n' > /tmp/h.md` + `--print` → exit 0，`content:""` | `readDigest` 增加「非空行不能全是标题」的检查 —— 变异 **M20** |
| 3 | **G3 断言超出了实现的承诺**：18432 B 是打包预算，单行装不下时会独占一条并超过它 | 一条 18990 B 单行 → 分片 **19259 B**，exit 0 | G3 拆成「硬上限对每条都成立」+「预算只在能按边界切分时成立」，并**新增 19 KB 单行 fixture 把中间这段断言下来** —— 变异 **M4** 仍会红 |
| 4 | **G9 根本没测「可点击」**：只断言 URL 子串还在。而 CommonMark 不自动链接裸 URL，digest 里全是裸 URL | 对照富文本组件文档；文档只列 `[文字](url)` | 投递层新增**裸 URL 链接化**（§2 步骤 3），G9 改为断言「无裸 URL 残留 + 链接文字即目标」—— 变异 **M19 · M21** |
| 5（附带） | 文档**确实**写了表格支持与「最多 5 行数据」—— §0.1 原来的「未知」是错的 | curl 直接取 `rich-text.md` 原文 | §0.1 已更正（结论不变，理由换了） |

**审查没提、我自己发现的第 5 个缺陷**：链接化把 digest footer 收尾的 `*` 吞进了 URL —— `*… skill: https://…radar*` 变成 `[…radar*](…radar*)`：链接指向一个不存在的地址，斜体的收尾符也被吃掉。在真实产物上一眼可见。已修（URL 字符类排除 `*`），并补了 fixture 与变异 **M22**。

**审查明确列出的「验过且干净」项**：签名算法、卡片 JSON 结构、20 KB 上限与官方文档一致；打包不变量在 3000 组随机 digest + 200 组分片用例上成立；30 分片 / 524 KB 的输入完整无损；单行超硬上限的拒绝路径正常。
